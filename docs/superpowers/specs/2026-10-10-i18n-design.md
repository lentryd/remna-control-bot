# i18n: English as the base language, Russian as the second

## Goal

Every user-facing text (bot messages, buttons, WebApp client screens, WebApp operator screens) is available in English and Russian. English is the base and the fallback. The language follows the Telegram `language_code` of the person using the product. Adding a language later is one catalog file per surface, with no code changes.

While moving the texts into catalogs, replace internal jargon ("админка", "провайдер", "панель", "квитанция", "аддоны") with plain, friendly wording.

## Non-goals

- A language picker UI. Language comes from Telegram only.
- Languages beyond `en` and `ru` in this change.
- Translating payment-service field names that the services themselves use (Shop ID, API token).

## Current state

- Bot texts are hardcoded Russian in Go: `internal/telegram/view/` (`texts.go`, `notices.go`, `screens.go`), `internal/telegram/bot.go` (command menu), `cmd/bot/main.go`, `internal/orders/` (admin alerts), `internal/payments/*` (`Title()`).
- The bot never reads `language_code`. `view` functions take data only.
- WebApp client uses i18next with `web/public/locales/ru/bot.json` only (`lng: 'ru'`, `fallbackLng: 'ru'`).
- WebApp operator screens bypass i18n (`web/src/pages/admin/text.ts`, `sections.ts`). `Overview.tsx` hardcodes "Админка".
- `initdata.User` does not carry `language_code`.

## Design

### Go: `internal/i18n`

- Catalogs `internal/i18n/locales/en.json` and `ru.json`, embedded with `go:embed`. Flat keys (`menu.subs`, `notice.expired`), `fmt`-style placeholders.
- `Bundle.For(code string) Localizer`. The code is normalized to its primary subtag (`ru-RU`, `ru_UA` → `ru`). An unsupported code selects `en`.
- `Localizer.T(key string, args ...any) string`. A key missing in the selected language falls back to `en`. A key missing in `en` returns the key itself.
- Pluralization (days left and similar) is handled with explicit keys (`_one`, `_other`) chosen by a small per-language rule function, so no extra dependency is needed.
- Parity test: every language has exactly the keys of `en`, with the same placeholders. A missing or extra key fails CI.

### Bot

- `view` functions and other text producers take a `Localizer`. All strings move to the catalogs.
- The language for a reply comes from the update's `language_code`.
- The command menu is registered per language (`setMyCommands` with `language_code`), with English as the default scope.
- Provider titles (`Title()`) become catalog keys.
- Golden tests in `view/testdata` cover both `en` and `ru`.

### Stored language

- New `user_lang(tg_id, lang)` table in `internal/store` (the bot has no users table; customers live in remna-control), created with the other tables on open. It is refreshed on every message, button press and WebApp open.
- Proactive messages (expiry notices, order cards to admins) use the stored language and fall back to `en` when it is empty.

### WebApp

- `i18n.ts`: `fallbackLng: 'en'`, language detected from `Telegram.WebApp.initDataUnsafe.user.language_code`, locales `en` and `ru` under `web/public/locales/`, loaded through the existing http backend.
- Operator screens move into the same locales as a separate `admin` namespace. `Overview.tsx` hardcoded text moves to keys.
- `<html lang>`, `dayjs.locale` and number/currency formatting follow the selected language instead of being fixed to `ru`. The base currency still comes from the backend.
- `initdata.User` gains `language_code`, so the server can store it when the WebApp opens.

### Wording cleanup

Rules: no internal jargon, short sentences, polite and warm tone, no bureaucratic style. Examples (final list is part of the plan):

| Now | en | ru |
|---|---|---|
| Админка / Открыть в админке | Manage / Open in Manage | Управление / Открыть управление |
| администратор (to customers) | support | поддержка |
| провайдер | payment service | платёжный сервис |
| панель | VPN panel | VPN-панель |
| квитанция | payment receipt | чек об оплате |
| аддоны | extras | дополнения |

Technical names that payment services use themselves (Shop ID, API token, Crypto Pay) stay as is.

## Testing

- Catalog parity (keys and placeholders).
- Locale normalization (`ru-RU` → `ru`, unknown → `en`) and missing-key fallback.
- Bot golden tests in both languages.
- Migration and language persistence (updated on activity, used by proactive messages, `en` when empty).
- Web: type-check and build; every `t()` key exists in both locales (same parity check as Go).

## Delivery
